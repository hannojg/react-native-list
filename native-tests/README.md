# Native runtime tests

This is a standalone XCTest / Android instrumented JUnit experiment. Each test
creates two Hermes runtimes and real React Native `ObjCTurboModule` or
`JavaTurboModule` wrappers around tiny native fixtures. It does not launch Expo,
Metro, a React root, or the example app. Android still needs a device/emulator for
JNI; iOS uses a hostless XCTest bundle on a simulator.

The shared C++ fixture explicitly drains each runtime's callback queue and Hermes
microtasks. Tests have no sleeps or timing-dependent expectations. This borrows
the deterministic scheduling idea from [Fantom](https://github.com/facebook/react-native/blob/v0.86.2/private/react-native-fantom/__docs__/README.md)
and the embedded-Hermes approach from [RN's native TurboModule tests](https://github.com/facebook/react-native/blob/v0.86.2/packages/react-native/ReactCommon/react/nativemodule/core/iostests/RCTTurboModuleTests.mm).
It does not depend on Fantom's private runner or bring in GTest/OCMock.

## Coverage

Both platforms check these four scenarios:

- Two runtime-local wrappers observe one native counter.
- Native callbacks and promise results reach only the runtime whose queue was drained.
- Separate native instances keep the root event listener working.
- Sharing one native instance keeps events owned by the root wrapper; the UI receives none.

On iOS, wrapper creation now uses UI List's production `BorrowedModule` adapter,
so the shared-instance event test passes. Android's shared-instance event test is
still **intentionally failing** with RN's current callback registration: the root
receives zero events instead of one, and the UI receives the event instead. The
Android implementation and adapter tests are the next change in the stack.

iOS additionally checks that root events survive UI-runtime teardown, creating
the UI wrapper first does not steal root events, and the borrowing adapter does
not initialize or invalidate the native instance or advertise native JSI binding
installation to the UI manager.

The wrapper method tables and event setup mirror codegen output and call RN's
actual conversion and callback-registration methods; these fixtures are not
generated by codegen.

iOS also exercises both actual managers through module lookup: the root creates
and initializes one native instance, the UI caches a distinct wrapper, native JSI
bindings run once, and invalidating the UI manager leaves root events and the
native instance intact. Only root manager invalidation tears down that instance.

There is a strict **expected failure** for handwritten C++ modules that own their
state inside their wrapper. iOS exercises the real managers' pure C++ lookup,
which creates two independent counters instead of sharing one backend. XCTest
matches only that assertion and rejects an unexpected pass, so fixing this case
requires promoting it to a normal passing test.

These tests do **not** exercise UI List's Worklets installer, Android's
`TurboModuleManager` or adapter lifecycle, Fabric view events, or Worklets
scheduling. The inline native invoker used by the routing tests does not model
native threading; the iOS manager test uses RN's real native queue selection.

The harness lives outside the published package. It compiles the selected
production adapter sources directly, without launching the example app.
The runtimes and headers come from the installed RN version (currently 0.86.2),
with RN's default Hermes V1. This is not a cross-version compatibility suite.

## Renderer routing

Run the lightweight Metro/proxy regression tests without building an app:

```sh
node --test native-tests/metro/RendererRouting.test.cjs
```

These check routing for native commands, public refs, text input state, and DOM internals; command
dispatch through the current UI-runtime Fabric node; native tag lookup; unmounted refs; and lazy
delegation to RN's renderer in the main runtime. They use Node's built-in test
runner and mocked native bindings, not a React Native runtime. App launches are
still required to verify the real component import and native mounting paths.

## Initialization constraints and alternatives

The iOS adapters create separate JSI wrappers for each runtime while borrowing
one root-owned native module. Initialization, native event callback ownership,
native JSI binding installation, and teardown remain with the root manager.
Sharing the root JSI wrapper itself is not safe across Hermes runtimes.

The current implementation still has version-sensitive dependencies:

- iOS uses the injected `RCTModuleRegistry`, not `RCTBridge.currentBridge`.
  However, constructing the second manager currently reads private manager
  dependencies through KVC and overrides `_createAndSetUpObjCModule`. Queue
  selection also reads the root's shared queue when the native module supplies
  none. A direct provider around the injected registry could avoid manager
  subclassing, but must preserve native queue semantics. An upstream dependency
  injection API would be the cleanest alternative.
- Metro routes RN's native command and public-ref imports through a
  runtime-switching proxy. Otherwise component imports initialize RN's main
  renderer in the UI runtime and reach the absent `RN$registerCallableModule`.
  There is no no-op registration stub. The alternative is upstream support for
  selecting a renderer per runtime; the current resolver depends on RN's private
  file layout.
- Borrowing currently targets codegen-backed native modules. Handwritten C++
  modules that keep state inside their wrapper are not supported; the strict
  expected-failure test documents this. Supporting them needs a shared native
  backend with separate runtime-local wrappers, not copying a JSI instance.

## iOS

`TurboModuleManager.h` and `BorrowedModule.h` are implementation-only CocoaPods
private headers. Exporting them in the Swift umbrella imports ReactCommon before
the Fabric headers and causes C++ declaration-visibility errors with RN 0.86.
Keep them private rather than adding transitive includes or disabling compiler
checks. Rerun `pod install` after changing this header classification.

After `bun install`, with CocoaPods and its `xcodeproj` Ruby gem available:

```sh
cd native-tests/ios
ruby create-project.rb
pod install
xcodebuild test \
  -workspace NativeRuntimeTests.xcworkspace \
  -scheme NativeRuntimeTests \
  -destination 'platform=iOS Simulator,id=<booted-simulator-UDID>' \
  -derivedDataPath build/DerivedData \
  CODE_SIGNING_ALLOWED=NO
```

The project generator produces only a hostless test target. Pods use RN's
standard dependency setup and prebuilt binaries; the generated project, Pods,
and build output are ignored. Run the generator before the first pod install,
not between pod install and xcodebuild.

## Android

With JDK 17, Android SDK 36, NDK 27.1.12297006, and a booted arm64/x86_64 emulator:

```sh
cd native-tests/android
ANDROID_HOME=<android-sdk> ANDROID_SERIAL=<device-serial> \
  ../../example/android/gradlew connectedDebugAndroidTest --console=plain
```

This reuses the example's Gradle wrapper, but runs the separate test library
project, not the example build. If the wrapper isn't present yet, run
`bunx expo prebuild --platform android --no-install` in `example` first, or use an
installed Gradle 9.3.1 executable in place of the wrapper. Reports are under
`android/build/reports/androidTests/connected/debug`.
