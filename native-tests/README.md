# Native runtime tests

This is a standalone XCTest / Android instrumented JUnit experiment. Each test
creates two Hermes runtimes and real React Native `ObjCTurboModule` or
`JavaTurboModule` wrappers around tiny native fixtures. It does not launch Expo,
Metro, a React root, or the example app. Android still needs a device/emulator for
JNI; iOS uses a hostless XCTest bundle on a simulator.

The shared C++ fixture explicitly drains each runtime's callback queue and Hermes
microtasks. Tests have no sleeps or timing-dependent expectations. This borrows
the deterministic scheduling idea from [Fantom](https://github.com/facebook/react-native/blob/v0.86.2/private/react-native-fantom/__docs__/README.md)
and the embedded-Hermes approach from [RN's native TurboModule tests](https://github.com/facebook/react-native/blob/v0.86.2/packages/react-native/ReactCommon/react/nativemodule/core/iostests/RCTTurboModuleTests.mm).
It does not depend on Fantom's private runner or bring in GTest/OCMock.

## Coverage

Both platforms run the same four scenarios:

- Two runtime-local wrappers observe one native counter.
- Native callbacks and promise results reach only the runtime whose queue was drained.
- Separate native instances keep the root event listener working.
- Sharing one native instance replaces the root event callback with the UI wrapper's callback.

The last test is a **characterization of RN's existing behavior**, not the desired
sharing policy. It intentionally passes when the root listener loses the event.
It gives us a small reproduction to change when we implement event ownership.
The wrapper method tables and event setup mirror codegen output and call RN's
actual conversion and callback-registration methods; these fixtures are not
generated by codegen.

These tests do **not** exercise UI List's installer, either platform's
`TurboModuleManager`, module lookup/initialization, manager invalidation,
`installJSIBindingsWithRuntime`, Fabric view events, or Worklets scheduling.
In particular, passing does not prove root-owned teardown or a safe sharing
implementation. Those need focused tests against the production manager changes
when we add them. The inline native invoker also does not model native threading.

Everything lives outside the published package and its build configuration.
The runtimes and headers come from the installed RN version (currently 0.86.2),
with RN's default Hermes V1. This is not a cross-version compatibility suite.

## iOS

After `bun install`, with CocoaPods and its `xcodeproj` Ruby gem available:

```sh
cd native-tests/ios
ruby create-project.rb
pod install
xcodebuild test \
  -workspace NativeRuntimeTests.xcworkspace \
  -scheme NativeRuntimeTests \
  -destination 'platform=iOS Simulator,id=<booted-simulator-UDID>' \
  -derivedDataPath build/DerivedData \
  CODE_SIGNING_ALLOWED=NO
```

The project generator produces only a hostless test target. Pods use RN's
standard dependency setup and prebuilt binaries; the generated project, Pods,
and build output are ignored. Run the generator before the first pod install,
not between pod install and xcodebuild.

## Android

With JDK 17, Android SDK 36, NDK 27.1.12297006, and a booted arm64/x86_64 emulator:

```sh
cd native-tests/android
ANDROID_HOME=<android-sdk> ANDROID_SERIAL=<device-serial> \
  ../../example/android/gradlew connectedDebugAndroidTest --console=plain
```

This reuses the example's Gradle wrapper, but runs the separate test library
project, not the example build. If the wrapper isn't present yet, run
`bunx expo prebuild --platform android --no-install` in `example` first, or use an
installed Gradle 9.3.1 executable in place of the wrapper. Reports are under
`android/build/reports/androidTests/connected/debug`.
